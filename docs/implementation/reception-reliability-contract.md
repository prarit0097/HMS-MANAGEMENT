## Design decisions and API/permission/failure contract

1. Patient demographic correction: existing PATCH patients/{uuid}/, existing patients.write and branch scope. Editable full_name/phone/age/date_of_birth/gender/city only; no branch/UHID/clinical editing. Show existing identity alongside edit action; retain form on validation/network error, refresh detail/list on success. No new clinical grant. Existing API has no demographic optimistic version; explicitly disclose remaining lost-update risk rather than invent signing safety.
2. Appointment reschedule: existing PATCH appointments/{uuid}/ with expected_version. UI exposes scheduled_at, doctor_name and reason for scheduled records only. Preserve patient identity, show device-local entry timezone/IST display.409 retains form and tells staff to close/reload latest record before another change; never silently overwrite. Existing backend state machine stays authoritative.
3. Patient picker: existing bounded patients?q&limit=25&offset across all matching records. Find resets page and selection; page change clears selection; show result range, previous/next and retry. Confirm UHID/name before appointment/admission; same phone not unique. No unsupported synthetic patient fallback.
4. Bed list: extend existing GET beds/ with optional status from existing exact status enum. Unknown status400. Filter in database before count/pagination and only inside authorised branch scope. Frontend board resets offset on filter change; admission picker requests status=available, pages matching beds; no current-page-only status filter or first100 cap. Zero available beds gives plain next step, API allocation concurrency still decides availability on save.
5. Optional Idempotency-Key UUID header on POST patients/, appointments/, admissions/; omitted header preserves existing API clients (duplicates can still occur for legacy callers, not a universal retry guarantee). Browser creates one key per logical create form, sends the same key on unchanged retry after ambiguous/network error and does not generate a new key automatically after failure. New logical form/successful completed create gets a new key. A corrected validation-rejected request may reuse its key because no record was committed.
6. Backend key namespace: authenticated user + operation + UUID key; payload fingerprint canonical JSON of original request body (sorted keys). Persist only fingerprint and result UUID/type, not request/response clinical/contact payload. Key and domain write commit together transactionally. Same key/body returns201 and same existing authorised entity, no second mutation/audit; result serialisation is current projection, not frozen historical response. Same key/different body409 with clear instruction to verify previous result before retry. Malformed/oversized key400. Key lifetime no expiry in this initial slice; retention/capacity is a later policy, not silently cleaned.
7. Every replay rechecks current authentication/action/branch/result visibility through the same scoped API/service ceiling before revealing a result. Revoked branch grants/disabled user cannot replay into access; no cached response bypass. Existing strictly validated related IDs/body still apply. Domain errors roll back idempotency record so corrected retry works. Concurrent same-key request creates at most one domain record; database uniqueness/locking and actual PostgreSQL tests prove this. Different users may use same UUID independently.
8. Frontend recovery: no automatic retries for writes; preserve entered values and logical key on transient failure. If user changes payload after an ambiguous success and receives key-conflict, explain to search/refresh existing records before starting a fresh registration/booking/admission. Do not silently rotate key to create a duplicate. No sensitive data/localStorage persistence of form payload.

## Pre-code reviews and acceptance tests

- Scenario/permission review: wrong branch, removed membership, inactive user, readonly doctor, master-only without operational grant; authorised reception success. API independent from UI.
- Threat review: key cannot grant authority, arbitrary/read-only fields rejected, bounded key syntax/input, no PII in request ledger, invalid status cannot bypass branch filters. Fingerprint avoids raw payload retention; authenticated actors still require future global quotas/rate limits.
- Failures: successful response lost, payload changed, validation fails, service transaction fails, concurrent replay, original entity later changed, stale reschedule, no available beds, patient beyond first25, branch switch while form open.
- Backend RED tests before implementation: same-key replay once; changed-body409; malformed400; validation failure key reusable; removed-grant replay denied; users isolated; status filtering count before pagination; PostgreSQL concurrent identical key produces one registration and one audit. Then code/migration and full backend suite, migration drift/check.
- Frontend RED tests: demographic PATCH fields; reschedule expected_version and409; patient second-page selection; available-bed server filtering; failed create retry sends same header, changed ambiguous payload does not silently get a new key. Then typecheck/full tests/build and inspect error/empty/keyboard behaviour.
- Root API source: add optional UUID Idempotency-Key to three POST operations and status query enum to beds GET before code. Page-action operations/permissions unchanged. Validate OpenAPI/map/docs and actual GitHub CI evidence separately; do not equate VPS tests to CI.
