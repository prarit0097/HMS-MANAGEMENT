> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans, RED-first tests and independent review. Coordinator alone commits/pushes.

**Goal:** Protect individual HMS sessions with optional authenticator enrollment and enforce MFA for privileged production writes, without treating a password-only challenge as authenticated access.

**Architecture:** Existing Django sessions/CSRF and authorised business services remain. ## Decisions and alternatives

- Coordinator ruling under existing implementation authorisation: use local authenticator TOTP with dedicated encrypted secrets, rather than hosted identity (new provider/cost/account decision) or unencrypted stock TOTP fields. Cost if insufficient is future federated identity/WebAuthn migration. TOTP is not phishing resistant; no claim of strongest assurance/full hospital readiness. Self enrollment is optional for ordinary roles in this slice; privileged unsafe platform writes require it outside development by default. Full recovery/organisation policy remains release work.
- Existing password-only login remains200 for nonenrolled users. Enrolled valid-password login returns202 pending MFA and never calls Django login before second-factor verification. Login starts a fresh anonymous server session; any prior authenticated state is cleared before challenge. All challenge/enrollment responses no-store. No password, TOTP secret, recovery code or URI in localStorage/sessionStorage, URLs, analytics, logs, audit or outbound QR service.
- Self security routes are available to authenticated individuals even without operational grants; they cannot edit anyone else. Admin staff reset/recovery are not included. Missing device/key cannot silently bypass MFA; owner/operator recovery needs separate reviewed process before real-data release.

## State, encryption and concurrency

- Add core0005: per-user IdentitySecurity with auth_epoch(default0), encrypted active factor/deviceUUID, greatest accepted TOTP step(initial-1), account attempt window/count, version. Separate pending enrollment UUID, encrypted160bit key, expiry10minutes and session binding; separate server-session-bound5minute login challenge with epoch and attempt budget; hashed single-use backup codes; shared network attempt budget. No GET creates state or audit rows. Exact model names can follow these meanings; record implementation names in living docs.
- TOTP30seconds,6digits preserving leading zeros,±1step drift. Select matching step then atomically require greater than last accepted across login, step-up, disable, backup rotation, password change and enrollment replacement. One accepted code cannot authorise two concurrent requests. Lock canonical user/security state consistently before factor/challenge/code use; actualPostgreSQL tests prove one winner.
- Pre-code independent review ruling: stable existing User row locks serialize first profile creation; then IdentitySecurity, challenge/enrollment/code, audit. Privileged writes acquire that same identity lock before organisation/resource locks and recheck captured epoch/proof/current membership, so revoke and protected write have a defined winner. Ordinary requests already in flight may finish; do not claim universal instantaneous cancellation. Preserve the epoch returned by the successful transaction, never reread/adopt a concurrent later epoch. Latest challenge uses authoritative generation/pointer, not only session data. Ciphertext includes version/purpose as well as identity/device binding. Backup code hashing covers the full random code and lookup remains user-scoped. Successful factor completion may reset fixed-window failures, password-only challenge creation cannot.
- Encrypt JSON payload including userID and device/enrollmentUUID with Fernet/MultiFernet. HMS_MFA_ENCRYPTION_KEYS is comma-separated Fernet keys, first encrypts, all decrypt; independent of Django SECRET_KEY. Validate key syntax without printing values. Missing/wrong key503 security_unavailable, no bad-code penalty and no password-only fallback. Decrypted identity binding must match row; swapped ciphertext fails closed. Never return stored active/pending secret from GET. Generate secrets only with cryptographic randomness; dedicated key provisioning/rotation/backup separation in operations docs, never Git. Development tests generate ephemeral fixture keys explicitly, no committed encryption key.
- Enrollment requires current_password and, if already enrolled, current factor proof. It creates/replaces only this session's pending setup, returns secret+otpauth_uri once; old active factor remains until successful confirmation. Confirmation requires enrollmentUUID bound to this same session/user, still-valid auth epoch and pending expiry plus its TOTP code. Success atomically installs factor, increments epoch/version, consumes pending, invalidates prior challenges and replaces recovery codes. Return ten recovery codes once; replay confirmation409/no secret replay.
- Recovery format8hex prefix-32hex random secret(128bits). Unique prefix lookup plus Django salted password hash of the entire normalized prefix-secret code, no plaintext DB. Ten codes; consume once atomically, replace all on rotation/enrollment/disable. Same-session lost response does not replay codes; regenerate with fresh proofs. Code list remains only in transient UI memory until acknowledged/closed; explain saving privately.
- Login challenge latest per user replaces earlier challenge; binds random session-owned identifier/server-side hash and epoch, not URL/body user ID. Valid password creates challenge only; methods totp/backup_code, expiry and generic code returned. POST verify consumes matching factor/challenge in one locked transaction, then Django login rotates session/CSRF and records proven epoch/verified_at. Failed/expired/used/cross-session challenge cannot authenticate. Logout is explicit CSRF-protected AllowAny POST to cancel full/partial sessions without leaking existence.
- All full sessions record auth_epoch and factor_verified_at. Middleware after Django Authentication rejects stale epochs on every authenticated API; legacy missing epoch accepted only while actual stored epoch0. Authorisation helpers and lock-protected sensitive services recheck session epoch/current proofs after waits; a middleware-only precheck cannot authorise a waiting revoked write. Direct internal services need trusted explicit session/access context, never adapter privilege. Enrollment confirmation/disable/recovery-code rotation/password change/revoke increment epoch and invalidate old challenges. Proved current session receives new epoch for changes/others-revoke; all-revoke logs out caller. Active membership ceilings continue separately.
- Account bad-factor budget5failures per5minutes, challenge5total attempts, shared trusted-IP10attempts/minute across workers including login/verify/security proofs. New challenge does not reset account failures. Canonical DB locks/atomic updates, fixed five-minute account window starting at its first failure (five failures block until expiry); challenge five-attempt lifetime remains independent and result objects ensure failure counters commit before adapter raises/returns400/429; never rollback counters in an exception transaction. No permanent lockout; Retry-After positive bounded seconds. Network key is hash of effective verified_client_ip from existing strict resolver, never untrusted raw XFF. Expired challenge401, invalid proof401, limit429, wrong/missing key503. Malformed nonobject/unknown fields400 before expensive work; invalid password/login remains generic401. No code/token echoed in errors. Rate-budget cleanup beyond bounded expiration is a later operations task and must be recorded.
