## Smaller coordinator candidate

Use one fixed root-owned systemd supervisor unit whose initial process is a root-controlled launcher. That launcher prepares its **own** launch identity, commits the expected tuple, drops privileges irreversibly and execs the fixed supervisor **in the same PID**. It introduces no custom parent/child handshake, SCM_RIGHTS broker or continuously privileged launch service. The earlier forked stopped-child protocol is superseded as a candidate direction, not as an approved implementation.

| Approach | Disposition and reason |
|---|---|
| Root parent creates/stops child, transfers descriptor, installs child's tuple and handshakes | Earlier candidate; additional child-lifetime, transfer and handshake states are unnecessary if a same-PID drop-and-exec sequence works on the pinned platform. Do not implement both. |
| Unix socket / peer credentials | Not selected for launch handoff. SO_PEERCRED is local connection-time identity, not executable/manifest authority; socket inheritance/passing and instance authentication remain separate problems. |
| Root wrapper becomes supervisor by irreversible drop and fixed exec | Coordinator candidate: root-owned descriptor and boot/PID/start identity survive the one intended handoff. Exact systemd, code/import closure, credential drop, cgroup and database transition still need their own reviewed acceptance. |

[Primitive evidence](../operations/document-launch-primitive-evidence-2026-11-15.json) demonstrated seals/mutation denial and fork inheritance. [Exec evidence](../operations/document-launch-exec-evidence-2026-11-15.json) demonstrated, in one isolated synthetic child, root-owned sealed read-only FD survival across fixed exec, matching PID/start/boot, dropped IDs and four capability sets, inability to regain root, and failure of an unprivileged copy to acquire root ownership. Exact child was reaped and the existing preview service remained active. This establishes **primitive feasibility only**, not this systemd launcher, descriptor wire grammar, application handle custody, Control install, scanner, SQL privileges, PID reuse, reboot, cgroup cessation or production acceptance. No persistent unit/user/config/DB/runtime changes were made by those probes.

## Fixed-unit and root-phase boundary

The proposed unit has one literal root-owned name, literal ExecStart, fixed cgroup and `User=root` solely for the initial root wrapper. Proposed `KillMode=control-group` covers that owned unit; numeric PID disappearance is not cessation. Before proceeding, the wrapper must prove no previous owned supervisor/descendant remains **other than its own current launcher process**. Do not require a literally empty current cgroup while the wrapper is in it. Require the fixed unit MainPID to equal this wrapper PID as well as the exact self-only membership condition. Empty/self-only membership alone does not prove a previous process could not escape its cgroup: prevention of escape, namespaces/delegation/permissions and descendant containment require actual tests. Unknown membership, old descendant or unproved prior stop keeps maintenance closed and blocks expected-instance replacement and slot release. The exact installed systemd/cgroup semantics, child placement and stop evidence remain acceptance gates. Never stop unrelated units, apps or shared cgroups.

Root phase is a security-sensitive trusted computing base: unit, interpreter, launcher, supervisor executable, configuration, dynamic libraries and all imported code must be root-owned, read-only to every runtime service, integrity-pinned and loaded through a closed reviewed path/environment. A root-owned script that imports a service-writable module is unacceptable. Root phase imports no application modules and consumes no service-writable EnvironmentFile, PYTHONPATH, LD_PRELOAD or other user-controlled import/loader input. Pin ownership/integrity of the full interpreter/native import closure and parent directories, not just the final files. No user-supplied command, environment, PID, executable, unit, pathname or config expansion is allowed. The unit must supply no general runtime root privilege; exact capability bounding, no-new-privileges, saved-ID handling and restart policy must be frozen against the pinned host. Use fixed `Restart=no` and no automatic boot registration: starting or registering this lifecycle requires the reviewed explicit maintenance procedure. A systemd active state or `Type=exec` success is not readiness. No fresh launch may reopen gates or bypass old-process cessation.

## Same-PID launch sequence to freeze

1. Ordinary ingress, application/MCP/job/byte/worker callers remain stopped under the parent closed-maintenance bootstrap procedure. Root verifies existing external installation/epoch/guard and approved runtime manifest. Expected-launch replacement happens only through that reviewed procedure, not from a request or opportunistic recovery. This launcher does not enable API/intake/download; any preceding API-enabled/readiness-bootstrap step remains separately authorised while ordinary callers stay stopped.
2. After previous owned cessation is proved outside database locks, capture the wrapper's own boot UUID, PID, kernel start ticks, fixed unit/cgroup identity and manifest. Mint **one** `supervisor_launch_instance` UUID, not a redundant launch-generation UUID. The wrapper and final supervisor use the same PID/start/boot identity across the single allowed exec. [Generation mapping](document-ingestion-generation-map.md) separately names scanner generation; a daemon replacement does not mint a supervisor launch.
3. Root creates one bounded launch-record memfd while still privileged, verifies root ownership and exact bytes, applies WRITE/GROW/SHRINK/SEAL seals, verifies them, reopens read-only and closes every writable duplicate. The record binds the fixed installation/epoch/instance/boot/PID/start/unit/cgroup/manifest identity and the root profile's resolved runtime UID/GID/supplementary-group allowlist. The bounded version1 format and FD checks below are candidate requirements; their actual implementation and acceptance remain unfrozen. A caller-provided memfd, JSON/environment copy, service-writable file or S1 dataclass is never trusted provenance.
4. In a short root-maintenance Control transaction compare the expected prior state and install the new complete expected tuple with readiness cleared and scanner registration fenced as the parent contracts require. No OS/FD/process/key or external non-database network I/O occurs under Control locks; ordinary database protocol/COMMIT remains part of the bounded transaction. Only a **known commit** authorises moving to handoff. A crash after this commit but before exec can leave a dead expected instance with readiness false; it changes no gate or counter, and is not evidence of successful launch. Recovery reconciles it under maintenance. Unknown ACK stays under maintenance and uses bounded authoritative rereads of the same intended instance UUID/tuple, before exec, with fresh outside-lock guard checks; do not remint instance, assume rollback, create a second process or continue on uncertainty.
5. After known commit, take fresh outside-lock guard/own-process observations. Closure/mismatch or failed verification prevents handoff/readiness without assuming the known install rolled back. Reject reason=restore even if guard mode is active. Close all maintenance DB sockets, key/secret and unknown handles; remove sensitive bootstrap state from the future supervisor environment and argument vector. Dropped-ID process code must have no root-maintenance credential or handle. Publisher credentials are separately supplied later under their own reviewed custody path, never by retaining/reusing a root DB socket or bootstrap environment. Python object cleanup alone is not proof of memory zeroisation; actual secret custody/import/FD acceptance must establish the chosen boundary.
6. Clear inherited supplementary groups, set only the exact installation-resolved four-group root-profile allowlist for avctl (guard-read, scan-ipc, av-ipc and signature-read), set **real/effective/saved** GID and UID to the fixed dedicated supervisor identity, clear effective/permitted/inheritable/ambient capability sets and enforce the frozen anti-regain restrictions. Verify the resulting IDs/capability/no-new-privileges policy before exec; any incomplete drop exits unavailable. The private same-named primary GID remains distinct; the four exact supplementary memberships grant only their named guard/IPC/signature surfaces, not broad/shared app privilege. The wrapper never remains as a privileged helper or forks a privileged long-running parent.
7. Keep only explicitly reviewed stdio and the read-only launch FD for one literal approved exec; temporarily allow that FD across this exec and fail closed if exec fails. The supervisor's first trusted startup path immediately sets `FD_CLOEXEC` on it. This prevents subsequent exec inheritance, **not fork inheritance**: every future child creation must explicitly close it before child code, and unrelated child paths must receive no DB/key/launch handles. Forked children cannot act as publisher because their live PID/start differs. Additional reexec is not silently approved; it must lose the descriptor and restart through the reviewed maintenance lifecycle.
8. Before each authorised readiness/registration phase, the trusted supervisor reader validates the exact sealed root-owned read-only descriptor plus live own boot/PID/start/unit/cgroup and approved runtime context outside locks. Detached bounded observations then enter the parent's short Control transaction, which compares exact expected launch, active guard/epoch/API and current scanner/readiness authority. After known commit perform fresh outside-lock guard/process checks before advertisement. Neither reading replacement UUIDs from Control nor possessing copied record bytes refreshes provenance.

This is not immutable-executable attestation. Exec preserves PID/start identity while replacing code; descriptor ownership and hashes do not prove code can never be replaced or a compromised supervisor cannot lie. The one allowed fixed transition, root-read-only pinned code/import closure, process isolation and trusted runtime code are explicit assumptions requiring evidence. No protection is claimed against root compromise, arbitrary code execution in the approved supervisor, same-UID ptrace/descriptor theft or hostile whole-VM rollback. Ordinary wrong-instance/forked processes must fail exact live-instance selection under those assumptions.

## Version1 launch-record format candidate

This is a closed internal startup format, not an API, caller parameter or standalone helper authorisation. The root-only deployment profile supplies one literal supervisor unit/cgroup, expected numeric runtime IDs/groups and per-boot host namespace policy; the root-owned fixed unit separately supplies the approved manifest hash. Root reads the root-only0700 profile only before privilege drop. Runtime reads only its own root-owned read-only metadata projection, independently manifest-hash-bound, containing its UID/GID/four groups, fixed peer UID allowlist, unit/cgroup and host namespace/boot policy; it never reopens the root-only profile. The projection contains no credential, key, patient data or mutable authority and supplies no extra group/DB grant. Exact projection ownership/mount/path checks are reconciled with the OS profile before leaf freeze. Symbolic OS names are resolved and validated only during reviewed installation; the supervisor never resolves a user/group name from the record, environment, DNS/NSS or request. Profile files/parent directories and the full interpreter/import closure must be root-owned and unwritable by runtime services. Record/profile identity fields are internal and omitted from staff responses and ordinary logs.

Wire bytes are exactly one canonical ASCII JSON object of **1..2048bytes**, no BOM, leading/trailing whitespace, final newline, comments, duplicate keys or additional/missing keys. Canonical encoding is sorted keys, separators `,` and `:`, ASCII output, no indentation; decode then re-encode must reproduce every original byte. Escaped alternative spellings, reordered keys, `-0`, exponential/fraction numbers, NaN/Infinity, booleans/nulls in numeric fields and JSON strings masquerading as numbers deny. Grammar permits exactly the one closed `namespaces` object and the one exact integer array below; no other nesting. Strict parsing is required before detached facts are formed; canonical shape is not authentication.

| Exact required key | Candidate value/check |
|---|---|
| `version` | JSON integer exactly1, with bool excluded. |
| `installation_id`, `restore_epoch`, `supervisor_launch_instance`, `boot_id` | Canonical lowercase UUID spelling `8-4-4-4-12` hexadecimal, nonzero UUID; exact matching with trusted current guard/profile/own process and locked Control as applicable. No UUID version ordering or automatic epoch adoption. |
| `pid` | Strict nonboolean JSON integer1..2147483647, equals live own PID and the root-captured same-PID handoff identity. |
| `start_ticks` | Strict nonboolean JSON integer0..9223372036854775807, equals own Linux process starttime field22, not a timestamp/deadline. |
| `unit` | ASCII literal from root-only profile; length1..128, syntax `[a-z][a-z0-9-]{0,118}\.service`. No template/instance/user-supplied unit name. |
| `cgroup` | ASCII literal from the same profile, length1..256, `/system.slice/` followed by the exact unit; no extra slash, `.`/`..` segment, colon, backslash, NUL, escaping or namespace-relative alternative. This string is bound by the approved manifest/profile, not a new database authority column. |
| `runtime_manifest_sha256` | Exactly64 lowercase ASCII hex characters, equal to the externally approved manifest hash supplied by the fixed root-owned unit. A record-provided hash does not choose a manifest or code path. |
| `uid`, `gid` | Strict nonboolean JSON integers1..4294967294; equal to the profile's installation-resolved dedicated numeric UID/primary GID and live real/effective/saved IDs. No root/overflow/coercion or runtime account lookup. |
| `supplementary_gids` | JSON array of exactly4 strictly increasing unique nonboolean integers1..4294967294; exact equality to installation-resolved avctl guard-read/scan-ipc/av-ipc/signature-read GIDs and live supplementary set. No wildcard/group-name/group-inheritance interpretation. |
| `namespaces` | Closed JSON object with exactly `user`, `pid`, `mnt`, `cgroup`; each is a strict nonboolean positive uint64 inode1..18446744073709551615 obtained by root setup from trusted kernel namespace handles, never a caller number. Live own namespace inode equality is required for all four; host-versus-dynamic policy below applies. |

There are exactly14 top-level keys, including the four-key namespaces object. Manifest binding is noncircular: the profile contains no own manifest hash; the approved manifest binds the raw profile SHA256, each fixed service metadata-projection SHA256 and relative immutable image/import closure, excluding its own bytes and the final fixed unit anchor that embeds its digest. The separately root-protected unit supplies that approved manifest hash; FD/Control carry the same hash. Root setup reads/hash-verifies raw profile and projection bytes against that manifest before using IDs/unit/cgroup; after drop the trusted runtime verifies only its own read-only projection/manifest, never the inaccessible root profile. Projection ownership checks alone are not a hash or namespace policy substitute. A profile ID/unit/cgroup change produces a new manifest and requires closed maintenance, not a runtime profile refresh. The manifest-bound profile binds unit+cgroup+UID/GID/groups together; a valid record cannot widen any profile value. The private primary GID and exact four supplementary GIDs implement the separately named guard/IPC/signature surfaces; this format grants no broad shared-app/object/KEK/database privilege. Unsupported host namespace/profile layouts deny instead of truncating/normalising into this candidate.

The first-slice per-boot profile/projection pins the current boot UUID and **host user, PID and cgroup namespace inode identities** measured during reviewed root installation/maintenance against the trusted host kernel setup. User namespace is mandatory: UID0 ownership observed inside another user namespace is not evidence of host-root creation. Root launcher and final supervisor must remain in those exact host namespaces. The mount namespace may be the systemd unit's newly created private mount namespace: root captures its actual inode into the sealed FD after unit namespace setup, then final supervisor compares live own mnt inode to that FD value. The immutable profile/projection specifies the approved mount policy/layout but does not pretend to predict a future mount-namespace inode. A namespace/boot mismatch denies even when JSON UUIDs, UID0-looking fstat metadata and cgroup path strings match.

A reboot changes boot/host namespace identities. This first slice has no automatic boot registration/profile rewrite or last-good fallback: keep maintenance/ingestion closed, manually refresh the reviewed per-boot profile/projections and produce a new approved manifest/unit anchor before a new launch. Dynamic unit mnt inode capture does not change the approved policy hash or create a new DB namespace column. Record namespaces plus live process checks are OS evidence; the DB still compares the existing exact launch/manifest tuple. Cgroup/UID/group/peer/host-namespace policy is transitively bound through manifest→profile/projection hashes, never accepted as an arbitrary caller override.

## Fixed descriptor handoff and trusted-reader candidate

Use the literal internal startup argument `--launch-fd=3` solely in the root-owned fixed ExecStart/exec vector; no arbitrary FD number, record pathname, JSON argument, URL or inherited caller override is supported. FDs0/1/2 are only the reviewed fixed stdio destinations, FD3 is the sealed launch record. Root closes every other descriptor, including maintenance DB/key/secret/writable memfd duplicates, before the one allowed drop-and-exec handoff. FD3 is temporarily inheritable for that exec only; the supervisor's single-threaded trusted startup immediately sets/verifies CLOEXEC before any application code, credentials, threads or child creation. Later children must close FD3 explicitly before child code because fork ignores CLOEXEC.

Reader accepts no FD/path parameter: it duplicates fixed FD3 into a private CLOEXEC descriptor before inspecting or reading, avoiding another thread's close/reuse of the original number. Under the approved single-threaded startup and trusted runtime custody, validate on that same private descriptor: `fstat` regular file, st_uid=0/st_gid=0, exact permission bits0400, st_nlink=0, and size1..2048; `F_GETFL` access mode exactly O_RDONLY, never O_PATH/O_RDWR/O_WRONLY, with no unsupported status flags (only pinned Linux O_LARGEFILE may additionally appear); `F_GET_SEALS` exactly F_SEAL_WRITE|F_SEAL_GROW|F_SEAL_SHRINK|F_SEAL_SEAL, numeric0x0f on the pinned Linux ABI. EINVAL/unsupported seals or additional unknown seal/status bits deny. Do not use a `/proc/self/fd` debug name, `memfd:` prefix, filename or bytes as creator proof: host-root ownership in the independently checked host user namespace plus the pinned launch/profile-projection/trusted-code boundary is the provenance assumption, not a cryptographic creator certificate. Another root process is inside the trusted root boundary; root compromise is excluded.

Perform one bounded offset-independent pread of at most2049bytes at offset0 on the validated private regular sealed descriptor. Require exact fstat size, no short/trailing/oversize bytes; interrupted/failed/unsupported reads fail unavailable rather than retry without bound. No read-before-fstat/seal check, pipe/socket/device read, blocking FIFO open, arbitrary path traversal, mmap, unbounded stream or wait-for-EOF is allowed. Recheck descriptor metadata/seals/flags after the read and require the same dev/inode/size/owner/mode/link tuple; close the private duplicate in all paths. Valid sealed content cannot mutate, but read-race/FD-custody failure is still denial, not permission to use cached bytes. No claim of a hard OS scheduling/physical-read SLA follows from these bounds.

Validate parsed facts against live own process **outside all database transactions/locks** each registration/publication phase: own boot UUID from fixed procfs boot source; own PID and robustly parsed `/proc/self/stat` starttime field22 (comm can contain spaces/parentheses); exact unified-cgroup2 `0::` own membership matching the fixed profile; host user/PID/cgroup namespace inodes and boot pinned by the validated own projection, plus dynamic own mount-namespace inode captured by root in the FD; UID/GID triples and supplementary groups, NoNewPrivs and capability policy. Unknown/multiple/unexpected namespaces/memberships or partial procfs reads deny. Compare approved fixed executable/interpreter/config/import closure to the manifest-bound own projection/image policy, without reopening root-only0700 profile; PID/start/boot continuity across exec does not attest code. Subsequent bounded DB comparison selects exact expected L, namespace and current scanner/gates, never performs procfs/profile/FD/scanner I/O while locked. Fresh postcommit observation is still required.

Any missing/wrong/closed FD, malformed/corrupt record, profile/hash/ID/namespace mismatch, parser/read/metadata race, permission/seal/drop error or uncertain install remains unavailable: no registration/readiness advertisement/claim, no record rebuild from Control, no default IDs/last-good cache/alternate reader, no automatic gate opening or counter release. Log only a fixed internal diagnostic reason with no record bytes, descriptor dump, credentials, PHI or raw scanner details. Initial startup failure exits the proposed Restart=no unit under closed maintenance; later validation failure fences local readiness and follows owned cessation/reconciliation without assuming committed DB state rolled back.

The earlier two synthetic probes did **not** test this14-key/namespaces parser, malformed/2048boundary/FD-race cases, full procfs/profile checks, arbitrary final interpreter import closure, live Control agreement or actual systemd FD custody. Required RED/acceptance cases include every closed-key/type/canonical failure,2048/2049bytes, root-looking normal file/pipe/socket/O_PATH/writable/unsealed/extra-seal FD, private-duplicate FD reuse race, fork/reexec/user-namespace UID0 forgery/boot-host namespace drift/dynamic unit-mount namespace drift/UID/four-group drift and fixed own-projection/profile mismatch. No test implementation or passing result is supplied here. Linux documents [memfd names as debugging only](https://man7.org/linux/man-pages/man2/memfd_create.2.html), [inode-wide nonremovable seals](https://man7.org/linux/man-pages/man2/F_GET_SEALS.2const.html) and [proc stat fields](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html); the whole launch mechanism remains a design inference requiring pinned-platform acceptance.

## Required scenario/threat/test matrix

| Case after a separately frozen leaf | Required outcome |
|---|---|
| Old descendant survives prior unit stop | New root wrapper does not install replacement tuple or release slot; prove fixed owned cgroup membership/cessation, excluding only current wrapper itself. |
| Root wrapper crash before/after expected-install commit, before/after drop or failed exec | Maintenance remains closed/unready; reconcile exact tuple and owned lifecycle, never speculate a successful handoff or auto-open gates. |
| Wrong root phase imports/config, writable executable dependency or caller environment | Fail before sensitive credential/expected-tuple use. Verify the complete root code/import closure, not just top-level script ownership. |
| Fork/SCM copy, service-created sealed memfd, writable duplicate or extra inherited handle | No authority from bytes/FD possession; root ownership/seals/RO mode and exact live identity required. Child handle audit proves explicit fork closure as well as CLOEXEC. |
| Initial exec / later exec / UID or capability-drop fault | Initial fixed exec preserves the intended identity; later exec cannot inherit launch authority. Verify saved IDs, supplementary groups, capabilities and failure to regain privilege. |
| Matching PID with reboot/reuse/wrong namespace/cgroup | Deny despite partial identity match; boot/start/unit/manifest/expected-instance conjunction remains mandatory. |
| Publisher paused before Control, root replacement, API/guard closure or unknown ACK | Old observations cannot adopt current identity or reopen readiness; fresh postwait/postcommit authority checks, no UUID/deadline reminting. |
| Same supervisor scanner replacement / new supervisor identical scanner hashes | Independent launch/scanner fences; no retagging old claims. Registration, idle renewal, active scan accounting and strict readiness cutoff follow reconciled contracts. |
| Copied restored enabled Control/descriptor, including mode=active with reason=restore | External epoch/closed maintenance and explicit restore-reason rejection deny use; no first-slice restore re-enable or anti-root/whole-VM rollback claim. |
