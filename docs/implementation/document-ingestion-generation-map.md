# Ingestion supervisor and scanner identity mapping

**DRAFT — 15 November 2026, Asia/Calcutta.** Bounded candidate for review, not a frozen schema, implementation plan, migration, executable acceptance or activation. Read with [launch proof](document-ingestion-launch-proof-draft.md), [guard authority](document-ingestion-guard-authority-contract.md), [runtime](document-ingestion-runtime-contract.md) and [persistence](document-ingestion-persistence-contract.md). No source, API, setting, dependency, OS or live change is supplied. Existing S0/S1/B3 delivery remains complete.

## Minimal identity set

Use **one `supervisor_launch_instance` UUID** for the exact root-authorised supervisor process lifetime, with the launch draft's immutable boot/PID/start/unit/manifest tuple. Do not also add `supervisor_launch_generation`: it has no independent transition or consumer beyond the instance and would create another equality field without another security property. UUID equality fences identity; it never authenticates process provenance.

Use **one `scanner_generation` UUID** for one daemon start plus its immutable engine/config/validator/signature snapshot. The existing DRAFT name `supervisor_generation` means this scanner lifecycle and is replaced by `scanner_generation` at every proposed consumer below. It must not represent the supervisor launch instance. Never infer either identity from the other, content generation, restore epoch, policy hash or readiness token.

Each new scanner start creates a new scanner UUID even with identical snapshot hashes. A signature/config/validator change requires the runtime's stop/snapshot/start sequence and a new UUID, not in-place mutation. Supervisor replacement requires old owned processes to cease; the replacement starts its own daemon and therefore also obtains a new scanner UUID. The identities stay distinct because a scanner can restart while its supervisor stays unchanged.

## Idle refresh and whole-attempt admission

Normal readiness refresh is **idle-only**, not renew-and-retag. The publisher collects genuinely fresh bounded observations outside locks, then its short transaction locks Control and rechecks current launch/scanner/API/epoch, the existing evidence rules and `scans=0`. Only that transaction may rotate the normal readiness token with new evidence/validity. With `scans=1`, normal renewal makes no mutation, even if the old evidence is nearing expiry. No new token, extended timestamp or rewritten claim follows a busy response. Fresh external guard/process checks still follow a known commit before advertisement; unknown ACK stays locally unavailable until reconciled.

Before committing a scan claim, lock Control in the parent order and acquire the remaining required claim rows. Take fresh server time **after the final row-lock wait**, using an actual current-clock sample rather than transaction-start `now()`/`CURRENT_TIMESTAMP`, then recheck active scanner registration/readiness and every applicable claim cutoff at the final authorising selection while Control remains locked. Compute the attempt's unchanged intended end from its original preclaim origin: `attempt_end=min(original_attempt_started_at+45s, original_cycle_deadline)`. In addition to all existing deadline/stage/cleanup-reserve checks, require current readiness valid now and `attempt_end < readiness_valid_until`. Do not shorten the attempt to the remaining readiness period to force admission, remint its origin, or extend readiness/lease/cycle deadlines. Equality is denied as well, preserving strict separation from the readiness cutoff without replacing the existing final-selection/cessation reserve. If the full intended deadline does not fit, issue no claim or scan slot; obtain an idle fresh observation through the ordinary publisher path before a separately authorised claim attempt. This is not a browser retry command or a new API capability.

Registration, claim, normal renewal, invalidation and cessation-confirmed release serialize on the same Control lock. The successful claim increments the durable one-scan slot and records the exact token/launch/scanner tuple atomically before any work. A renewal that acquires the lock later observes `scans=1` and does not rotate; a claim that acquires it later must select the newly committed readiness tuple. Lost claim ACK retains the persisted slot until outcome/cessation reconciliation; neither a timeout nor token expiry assumes it free. Final selection/promotion and its scan-count mutation use the same locked Control accounting; never decrement before the frozen completion/cessation rules permit it. Promotion preserves the original exact-token/current-authority checks and existing reserved cessation interval.

Fault, API/guard closure, scanner/launch replacement or evidence expiry can invalidate readiness while a scan is active; normal renewal's idle condition must not delay this safety action. Such invalidation makes the old claim stale and prevents promotion. It does **not** retag the attempt, reset accounting, release the slot, permit a replacement daemon or forgive uncertain writer/process cessation. Only the existing cessation-confirmed release transition can release the slot. Unknown invalidation ACK never implies that readiness stayed valid or that the slot disappeared.

A proposed readiness window of at most60s, a capped45s complete attempt and one scan slot yield at most an approximately15s fresh-window margin before a full45s attempt no longer fits, and do not prove useful throughput: slow evidence gathering, claim ACKs, lock waits and final selection can consume the margin. Idle refresh must retain actual observation age and absolute expiry; no timestamp extension is allowed to improve liveness. Scanner registration before first publication, renewal scheduling, exact typed busy/expired outcomes and actual PostgreSQL/Linux/capacity acceptance must be frozen together. This is a fail-closed candidate, not measured liveness or a hospital capacity claim.

### Literal scenario, threat and test matrix

| Executable case after leaf freeze | Required observation |
|---|---|
| Claim wins Control lock; renewal waits | Claim tuple and scans=1 commit together; normal renewal returns busy without changing any readiness/claim field. |
| Renewal wins Control lock; claim waits | Claim samples server time after its wait and selects only the new committed token/evidence; stale supplied token cannot be silently retagged. |
| Full intended end equals validity / exceeds it by smallest supported precision | Both deny claim with no slot/ordinal issuance, shortened attempt or reminted origin. A strictly earlier end can pass only if all other strict parent cutoffs and final-selection/cessation reserves also pass. |
| Evidence expires during claim lock wait or at final authority selection | No fresh authority from the pre-wait clock; no claim/promotion beyond the applicable cutoff. |
| Busy normal renewal near expiry | No ready-time/token/lease extension; active claim keeps original evidence. Safety expiry invalidation remains permitted and old claim cannot promote. |
| Fault/replacement invalidation races with busy claim | Deny stale promotion; scan count stays1 until proven cessation, with immutable old attempt identities. No implicit daemon replacement. |
| Claim/refresh/release COMMIT ACK lost | Reconcile original tuple and durable scan count independently; no double claim, fresh-time concealment, token adoption or speculative slot release. |
| Repeated idle refresh under API close, external guard mismatch or wrong launch | No readiness/gate opening from a valid-looking UUID or publisher request; no OS I/O under Control locks. |
| Long queue and scanner update | Bound waits and fail closed when original end cannot fit; no throughput assertion without measured liveness/coexistence evidence. |

## Client, API and acceptance effects

No changes to the current 50 implemented HTTP operations, S1 facts grammar, B3 receipts or existing CurrentUser shape. The five ingestion APIs remain proposed. Launch/scanner UUIDs, OS tuple and engine evidence are internal, excluded from staff JSON, error strings, MCP and ordinary logs. Optional future availability uses the parent boolean capability projection; it does not expose or accept these identity fields. Frontend does not choose generations, retry scan claims or manufacture readiness. No user-facing field/page/action is added by this mapping.

Required executable cases after leaf freeze: same supervisor with scanner replacement; supervisor replacement with identical snapshot; old publisher paused before Control lock; wrong-instance same-UID/fork/reexec subject to the launch threat model; unknown ACK at installation/renewal/claim/result; readiness renewal while a claim waits; stale result cannot be relabelled; copied restored Control cannot reopen; immutable accepted history survives routine update. Prove OS evidence is collected outside business locks and final generation comparisons occur after lock waits. These are a test design, **not tests run or passing evidence**.
