# Patient document metadata: transaction, limiter and quota feasibility review

25 October 2026. **DESIGN REVIEW / proposed freeze amendment; no implementation or PostgreSQL measurement.** Read with the metadata contract, metadata lock design and frozen dormant foundation. This review owns no production code, deployment, grants or resource provisioning. Coordinator must integrate accepted rulings into the exact execution contract before RED/code.

## Engineering rulings

Use the existing PostgreSQL17, Django5.2.18 and psycopg3.2.12 stack. Retain server-side lock and statement limits, add PostgreSQL17 transaction_timeout as defence in depth, and explicitly withdraw a hard five-second request/COMMIT acknowledgement guarantee. Choose a database-backed actor limiter committed separately before the audited business transaction; neither Redis nor process-local cache is needed. Keep scope derived from Patient/Branch, without adding an organisation column to document rows. Existing quota queries are correctness-feasible but their scan cost requires actual PostgreSQL EXPLAIN evidence; a LIMIT bounds returned rows rather than all work.

Alternatives considered: Redis introduces an unnecessary dependency; process-local counters cannot enforce a shared ceiling; counting successful DocumentAccessEvent rows both misses denied traffic and rolls back on audit failure; a limiter inside the business transaction loses its increment on ordinary rejection. Choose the small durable actor-state design below. This is an engineering recommendation requiring coordinator freeze, not recorded owner policy.

## Commit, constraints and actual timeout boundary

Local source inspected: backend/requirements.txt pins Django5.2.18 and psycopg[binary]3.2.12; backend/hms/settings.py currently supplies sslmode only and has no connection/operation deadline. The installed connection.py commit() calls wait(_commit_gen()); _commit_gen() sends COMMIT. The polling interval in wait()/waiting.py repeats until completion and is not an operation timeout. cancel_safe(timeout=...) bounds its cancellation exchange, not the original COMMIT or subsequent transaction outcome. Do not monkeypatch psycopg wait(), mix foreign-thread Django connection ownership, or invent a synchronous socket read_timeout option. Tagged [psycopg3.2.12 source](https://github.com/psycopg/psycopg/blob/3.2.12/psycopg/psycopg/connection.py) supports this inspection.

The public service must reject both connection.in_atomic_block and autocommit=False BEFORE consuming limiter allowance or touching document scope, then use atomic(durable=True) for each of its two sequential phases. Explicit rejection is necessary: installed Django Atomic permits the TestCase wrapper exception and treats autocommit=False specially; durable=True alone is insufficient to express this service contract. Use transaction=True tests/TransactionTestCase for real service success and explicit negative tests for ambient wrapping. No ATOMIC_REQUESTS wrapper for these operations.

For each phase, immediately after entering its outermost transaction and before acquiring domain locks, issue transaction-local lock_timeout='2s', statement_timeout='3s', transaction_timeout='5s'. Require server_version_num>=170000 for the production metadata implementation, failing503 rather than silently dropping the transaction control. Do not change connection-global settings or unrelated endpoints. PostgreSQL17 documents transaction_timeout as terminating a session that remains in a transaction too long, including explicit transactions; it is a server-session safety mechanism, not proof of prompt client delivery or rollback after an uncertain commit. Its interrupt processing also does not defeat an OS/storage stall. [PostgreSQL17 timeout documentation](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-TRANSACTION-TIMEOUT).

One monotonic application budget starts at public-service entry, including the limiter phase. Five seconds is a cooperative work budget: check before each business stage, after potentially blocking work and before commit; do not begin the main phase after exhaustion. It cannot interrupt a blocked synchronous driver call or guarantee receipt within five seconds. A separate wall-clock started_at/selected_at check rejects clock reversal and governs expiry. No automatic retry loop. Two phase-local five-second server controls do not imply one five-second total server or HTTP guarantee. Record actual healthy test durations separately; do not round measurements into a universal SLA.

Within the main phase: acquire the frozen lock chain; validate current authority/scope; apply command or choose read IDs; insert complete receipt if needed and the mandatory event; execute SET CONSTRAINTS ALL IMMEDIATE; finish any remaining bounded DB reads/network evaluation; then capture the final wall-clock selection instant, perform final pure authority/expiry/budget checks and materialise/encode the bounded detached response. No further writes or set-to-deferred command follow constraint forcing. This is safe precisely because the service owns the transaction and cannot force a caller's unrelated deferred work. CHECK and nondeferrable unique checks already run immediately; SET CONSTRAINTS retroactively checks deferred FK/constraint triggers and leaves them immediate. [PostgreSQL17 SET CONSTRAINTS](https://www.postgresql.org/docs/17/sql-set-constraints.html).

Final policy evaluation must use a coherent policy read and finish all blocking reads before the selection instant; any operation added after selection which can wait requires selection/authority/expiry revalidation. Keep actor/org/patient/intent locks through successful commit. A withdrawal's stored withdrawn_at may be the earlier attempted transition instant, but the final selection must still be strictly before expires_at; otherwise rollback all domain/receipt/event writes. Projection and can_withdraw use final selected_at, even when expiry crosses during audit/constraint wait. Do not promise withdrawal is still unexpired when the browser receives it.

Only release detached values after atomic exits successfully. Catch exceptions outside the atomic boundary. A normal rolled-back failure means domain/receipt/event are absent; connection loss during COMMIT is **unknown**, never labelled rolled back. Return generic503 when execution returns with uncertainty, discard the suspect connection before reuse, and allow a later explicit same-key request to reconcile receipt state under current authority. A retry may find the complete committed intent+receipt+event or safely create the missing command. Do not attempt compensating deletion, reset quota history, or replay automatically. If a driver call hangs, this process may be unable to emit503 promptly; worker/edge timeout and network-fault acceptance are separate deployment gates, not delivered by this source contract.

connect_timeout only governs establishing a connection; TCP keepalive/tcp_user_timeout are platform-dependent dead-peer mitigations, not complete receive deadlines when the server has acknowledged COMMIT but its reply is lost. No new DB alias/pool/watchdog/process-supervision design is necessary for this source slice. [libpq connection controls](https://www.postgresql.org/docs/17/libpq-connect.html#LIBPQ-PARAMKEYWORDS).

## Minimal shared durable limiter amendment

Add exactly one proposed core model DocumentMetadataRateWindow with actor OneToOne primary-key/FK User PROTECT, window_started_at required aware timestamp, admitted_count positive small integer CHECK1..60. No patient, document, IP, payload, filename, denial reason or append-only event table. Row count is bounded by actors who use this feature; rows are reused, never created per request. The actor unique/PK index is sufficient. Use one additional migration with a reverse-first guard refusing removal while any limiter row exists; retain existing foundation reverse guards, and test historical migration restoration to the actual graph leaf. This is the only mandatory schema addition in this review; no foundation constraint needs weakening.

Proposed algorithm: **fixed UTC minute windows**, aligned by flooring the authoritative server wall clock to a whole minute. All four operations share one actor row across every worker/branch/org. Fixed windows allow up to120 admissions across adjacent minute edges and must be described as such in contract/OpenAPI/test text; they are not a rolling-minute promise. If the coordinator requires an exact rolling60-second ceiling instead, do not silently ship this algorithm: freeze a bounded<=60 timestamp-ring design and its storage/type constraints separately before implementation.

Phase A, before any patient/document lookup: lock fresh actor User NO KEY UPDATE, lock existing IdentitySecurity if present, validate active identity/captured epoch and the action's global grant conjunction (branch-specific scope is checked only later). Lock existing limiter row after User; if absent create it under that stable actor lock. Existing shared User lock makes first-row creation race-free for supported services; DB uniqueness is backstop. Keep expiry calculations server-side, never from visitor input. In the same minute count<60 increments and commits; a later minute resets start/count=1; a backwards time before stored window start fails503 rather than resetting. At count60 return429 with ceil(window_end-now) clamped1..60 after leaving the phase; do not grow a denied counter. Exact equality at window_end resets.

Only after successful limiter commit start the existing business lock chain afresh, rechecking captured authority/scope after every wait. Releasing phase-A User before acquiring it again creates no permission bypass because phase B reauthorises; it also avoids a new cross-phase lock cycle. Never hold an org/patient/receipt/intent lock while entering the limiter transaction. Unknown phase-A commit means503 and no business phase; an allowance may have been consumed, which is conservative. No allowance refund.

Unauthenticated/stale-session/no-action-grant/CSRF/transport-invalid requests rejected before the public service do not consume this limiter; they remain subject to existing ingress/auth protections. A service-admitted request consumes allowance even if later exact-scope checks give403/404, changed replay gives409, enabled policy/dependency checks give503, quota gives429, or audit/commit fails. New-key/identical-key retries each consume one admission. Limiter unavailable/read/write/commit failure fails503 before PHI and never falls through to business work. A fail-before-commit cannot honestly promise its increment persisted. Test authenticated valid-action foreign patient traffic explicitly.

Limiter accounting is low-content operational state, not document disclosure audit. It must not create a fictitious DocumentAccessEvent for a denied/inaccessible patient. No additional patient-bound audit is required to increment/reset this counter. Existing mandatory successful-disclosure audit remains unsampled and in phase B; its failure rolls back phase B but preserves a successfully committed phase-A admission. If any future limiter-specific audit is mandated, it must commit in phase A and its failure must prevent admission; do not quietly add a best-effort audit path now.

## Quota correctness, queries and indexes

Under the already frozen single patient organisation gate and Patient lock, before a genuinely new create (not matching replay): select up to20 active IDs/expires_at for that patient where status=pending and expires_at>quota_now, ordered expires_at,id. If20 exist, reject429; earliest expiry gives a conservative Retry-After (withdrawal may free space sooner). Then select up to1000 organisation intent IDs/created_at where patient.branch.organisation=locked_org and created_at>quota_now-3600seconds, ordered created_at,id. If1000 exist, reject429; earliest retained creation +3600seconds gives retry. Exact boundary created_at==cutoff is outside the rolling interval. Count every successful create regardless of later withdrawal/expiry, across branches; receipts/events/replays do not count. Both thresholds may conservatively include rows which expire during the transaction, but must never undercount current successful admissions. Supported creators hold the same org gate until commit, so different actors cannot overshoot. Rollback frees the tentative intent naturally; unknown commit is reconciled, never assumed free.

Use one quota_now after required locks, and preserve the exact stored created_at used for rolling quota/expiry on new create. Because creation timestamp is assigned before commit, a long transaction can spend part of its window before visibility; the serialized check still prevents more than1000 currently retained created_at-window rows. Final selection may be later and project expiry; do not revise a replay's created_at. A backwards final clock fails503. Declare this timestamp-window semantics explicitly rather than asserting rolling committed-response time.

Existing patient-time-id index supports list keysets and patient-local creation ranges. Existing status-expiry-id supports an expiry range but is global; it does not guarantee efficient patient-active selection. The organisation rolling query joins existing indexed Patient.branch/Branch.organisation FKs; no foundation organisation column is added. LIMIT20/1000 bounds application materialisation, not scanned rows, joined patients, sort or elapsed work. Keep statement timeout and fail503 on timeout. Before source acceptance, EXPLAIN(ANALYZE,BUFFERS) on synthetic large expired-history/many-patient/multi-org data must show acceptable plans; preserve exact fixture size/plan and actual timings. Do not claim constant-time or durable capacity from these limits.

Potential index amendment only after an observed bad plan: conditional index(patient,expires_at,id) WHERE status='pending' for active quota. An organisation rolling query may still need a different approved design if actual plans exceed budgets; do not add global created_at indexes or duplicated org scope merely on speculation. This performance gate may remain open until coordinator's real PostgreSQL run; correctness unit tests cannot close it. No retention deletion, metadata/audit total cap or real-record activation approval follows from these quotas.
