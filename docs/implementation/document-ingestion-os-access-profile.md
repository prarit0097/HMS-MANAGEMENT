## One fixed root profile

Use literal `/etc/hms-ingest/access-profile.json`, root:root0600 within root:root0700 `/etc/hms-ingest`; all ancestors nonsymlink and root-controlled. The versioned closed profile maps fixed service/unit names to numeric UID, primary GID, exact supplementary GIDs and fixed unit/cgroup paths/peer UIDs. It omits the runtime-manifest digest. It contains **no secrets**, commands, arbitrary units, user-chosen paths or executable/environment expansions. Root pins its hash in the approved launch/runtime manifest. The launcher reads it during root setup only. Runtime uses the immutable own-service projection below, never reopens this0600 root file and never receives authority to rewrite membership.

The binding is deliberately non-circular: create the closed root profile first; the approved runtime manifest contains `access_profile_sha256=SHA256(raw profile bytes)` and relative executable/import-closure paths, never its own hash or an absolute path containing its own hash. The literal root-owned unit/image path supplies the approved manifest hash; root loader computes the actual manifest hash, verifies the profile raw-byte hash and exact IDs/unit/cgroup before sensitive setup. The launch FD carries the approved manifest hash, transitively binding this profile. Neither profile nor manifest discovers/adopts the other's current hash from writable runtime state. A profile/allocated-ID change requires a new reviewed manifest and closed-maintenance deployment, not runtime adoption. Exact byte/grammar/hash validation and root-unit binding remain leaf acceptance gates.

### Read-only own-service projection and boot anchors

Generate one fixed `profiles/<service>.json` within the approved root image from the root profile, with root:root0444 file and root:root0555 ancestry. It contains metadata only: that service's own real/effective/saved UID and primary GID plus exact supplementary GID list, required peer UIDs, literal unit/cgroup identity and namespace policy, plus the source profile raw-byte hash. No secret, command, loader override or own/runtime-manifest hash appears. The approved manifest binds `SHA256(raw own-service projection bytes)` at that relative path as well as the root-profile hash; neither file includes the manifest's hash. Runtime reads only its fixed own-service path under the already approved image, verifies its manifest-bound raw bytes and compares actual IDs/groups/peer policy; it cannot select another service's projection to gain rights. Runtime never reopens `/etc/hms-ingest/access-profile.json`, and metadata readability conveys no group/key/DB/launch authority. Read-only mounts and ancestry/path checks remain required, not inferred from mode bits alone.

The root profile is a **per-host-boot** profile: at future explicit root installation capture the current host boot UUID and host user-, PID- and cgroup-namespace inode anchors from the trusted host context. Do not hardcode observed numeric namespace IDs, predict them from a service name or auto-update anchors at startup. Each own projection carries the fixed required host-anchor policy. A boot/required-anchor mismatch fails closed and needs manual closed-maintenance profile/manifest refresh; `Restart=no` and no automatic boot registration remain unchanged. Root selects the host context before private unit namespaces, not by trusting a caller's `/proc` view.

The supervisor's mount namespace may be unit-private: its actual live namespace identity is captured at root launch and bound in the launch record through the separately reviewed namespace mapper; this static profile does not predict a future mount-namespace inode. Kernel procfs/nsfs descriptors, filesystem types, trusted mount ancestry, namespace device/inode identity and resistance to replaced/bind-mounted proc views require actual namespace-attack tests. An inode integer, path string or root-owned JSON file alone does not authenticate the observing namespace. Exact anchor grammar/lookup and dynamic launch-record namespace comparison remain open leaf gates; no namespace is created or inspected by this document.

Do not invent numeric IDs. A future reviewed installation must collision-check names and UID/GID numbers against existing users, groups, files, running services and all other apps, reserve distinct non-login service IDs, then write the root profile. Mismatch, duplicate ID, foreign ownership, NSS ambiguity, unexpected supplementary membership, writable ancestor or manifest drift denies startup; never `usermod` a pre-existing unrelated account to make the profile fit. No account, group, directory, ACL or unit is provisioned here.

## Exact service and group ceiling

Every service uses its own same-named primary group, no login shell, no app/admin/sudo/docker/www-data membership, no role inferred from name. Supplementary groups below are the **entire** allowed set, not examples. Group membership grants only the named filesystem/IPC surface; it grants no database role, key access, service control, patient scope or launch authenticity.

|---|---|---|

| `hms-ingest-bytes` byte service | `hms-ingest-guard-read`, `hms-ingest-object-read` | Guard; exclusively create/seal/publish encrypted objects through typed services; its own UID-private key/DB credential delivery. No clamd/control socket or supervisor SQL functions. |
| `hms-ingest-work` worker | `hms-ingest-guard-read`, `hms-ingest-object-read`, `hms-ingest-scan-ipc` | Guard; read encrypted original objects; connect typed supervisor socket; own UID-private keys/scoped DB credential. No direct clamd access or publisher credential. |

The guard-read group contains only preview/bytes/work/avctl. These narrow groups are explicit exceptions to the older blanket no-supplementary-group draft, **not shared-app groups**. Root's administrative access does not require group membership. No frontend, MCP client, other hospital portal or other VPS app joins any group.

## Irreversible handoff and children

Correct the old launcher phrase “clear all supplementary groups” to **clear inherited groups, then install only the exact root-profile whitelist while still privileged**. Empty final supplementary membership would prevent avctl from reading the guard and connecting private IPC. Set and verify exact supplementary GIDs, then set real/effective/saved primary GID and UID, clear the frozen capability sets and enforce anti-regain/no-new-privileges. No `initgroups`/NSS expansion from a caller or inherited service manager list. Verify the actual resulting numeric list equals the profile; excess and missing membership both fail closed. No runtime membership change, setgid helper, general sudo/polkit or service administration is granted.

The proposed fixed supervisor unit is `hms-ingest-avctl.service`, distinct from existing fixed `hms-ingest-clamd.service`. Root owns each literal unit/cgroup definition; supervisor wrapper initially runs as root only for reviewed setup and drops irreversibly before fixed exec. `Restart=no`, no automatic boot registration and no automatic gate opening apply. Fixed unit MainPID/cgroup and old descendant/escape-prevention acceptance still gate launch. The existing narrow daemon lifecycle control design is a separate freeze obligation; these groups give no generic systemd/D-Bus or arbitrary start/stop authority and introduce no new general broker.

Decoder/scanner/updater children must receive their own exact UID/GID/group and namespace profiles through a separately reviewed fixed launch path. A dropped worker/supervisor cannot regain root to set arbitrary child IDs. Do not call `setgroups` after privilege loss and silently fall back to the parent's groups. Clear launch/DB/key/unknown FDs before any child code; CLOEXEC alone does not prevent fork inheritance. No child inherits the parent's supplementary whitelist or publisher identity by default. Exact child launcher/namespace enforcement is an open implementation gate, not a delivered setuid facility.

## Credentials are UID-private, never group-shared

Use separate fixed UID-private runtime credential leaves beneath root:root0711 `/run/hms-ingest-secrets/` (traverse without listing): `bytes/`, `work/`, `avctl/`, owned by the respective UID/private primary GID0700; individual delivered files0400, exact owner UID and no extra ACL. The0711 parent allows only traversal, not listing, and0700 leaf denies cross-UID traversal; fixed mount/namespace policy limits each service to its own leaf. No IPC, object or guard group receives secret access. The exact provider/mount/refresh contract remains a gate; this candidate directory model does not claim physical zeroisation or resistance to compromise of its authorised UID.

Byte/worker key copies and scoped DB credentials are delivered separately to their own leaves under the existing proposed key facility, never through shared group files. Avctl receives only the dedicated lifecycle/readiness publisher credential after root handoff, no KEK or general application/migration login. Root maintenance DB material is root-only and never copied to these leaves, arguments or environment; every root DB socket/key/unknown handle is closed before final drop/exec. Credential delivery must not restore root privilege or reuse the bootstrap DB connection. Scanner/decoder/updater have no credential leaf at all.
