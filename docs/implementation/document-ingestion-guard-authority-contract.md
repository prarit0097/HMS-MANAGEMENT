## 1. Selected authority boundary

Use fresh bounded external-guard observations **outside every business transaction**, then compare their identity with the locked singleton Control and evaluate current database gates inside the transaction. Database authority is selected under those locks; its durable effect depends on resolved COMMIT. Read the external guard again **after releasing all locks and after known commit**, before returning a patient-bearing projection or selecting the first download byte. Never call filesystem, key-store, scanner, process-control or network APIs while holding business locks.

These are separate observations, not an atomic filesystem-plus-database transaction. A valid outside-lock read does not prove the guard remains active through a lock wait, physical COMMIT, reply or stream. A successful postcommit read does not prove it remains active one instruction later. Closing a file alone cannot instantly revoke a selection already made. The safety boundary for replacing state is the root maintenance protocol in section 6: close database gates, fence and stop/drain all owned processes, then replace state only after confirmed cessation and an independently durable closed restore guard. No timestamp, HMAC, broker or stronger-sounding cache turns the file into an atomic anti-rollback oracle.

This direction deliberately keeps the existing external guard and the proposed Control epoch/gates, rather than adding another distributed authority service. Control needs the retention candidate's immutable `installation_id` in addition to `restore_epoch`. Its normal gated operations compare both identity values for equality; epochs have no ordering interpretation. There is no first-slice restore re-enable or operator API.

## 2. Exact guard observation contract

Use only the retention draft's fixed `/var/lib/hms-ingest-control/epoch.json`, root ownership, directory0750/file0640 and narrow `hms-ingest-guard-read` reader group. Application discovery/admission, bytes, worker and supervisor UIDs may read control metadata only. Scanner/decoder/updater and arbitrary client principals are excluded. No additional shared key/content/DB privilege follows from this group.

Each mandatory observation reopens the current fixed basename relative to verified trusted directory descriptors; verify nonsymlink ancestry, no-follow/close-on-exec, regular-file/root-owner/exact-group/mode/no-extra-ACL rules. Read at most4097 bytes; reject more than4096, duplicate/extra fields, malformed types, noncanonical UUIDs or invalid mode/reason/timestamp/hash. Preserve the retention draft's closed version1 grammar. An old open inode, startup cache, arbitrary path, caller assertion or fallback mode is never an observation. Root atomic replacement can still race the read; the result describes the file selected by that open, not every later filesystem state.

Proposed internal immutable `GuardObservation` contains validated installation/epoch/mode/reason, local monotonic observation start/end, and the owning invocation/boundary identity. It is constructed only by the trusted reader, never accepted from JSON, HTTP, jobs or MCP. It grants no authority by itself. `recorded_at` is provenance, not a TTL or a lease. Do not silently mint this type from a bool/dict or deserialize a past success receipt into it.

One observation may serve exactly one immediately following transaction attempt at the named boundary. Perform ordinary non-I/O scalar preparation first; then observe, then enter that transaction without intervening body/object/scanner I/O. After lock waits, enforce the original context's wall and monotonic deadlines and transaction ceiling; compare the observation's identity to current locked Control. There is no invented universal millisecond freshness SLA: waiting is bounded by that operation's remaining budget and short transaction ceiling, not evidence the file stayed unchanged. A retry, deadlock, lock timeout, separate phase, reconciliation or unknown-ACK lookup requires a new observation outside a new transaction. It never remints the original first-binding deadline.

Postcommit observations are separately constructed and consumed only for the immediate detached response/first-byte boundary. They must be active and match the exact installation/epoch selected in the committed transaction. Missing, unreadable, malformed, closed or mismatching observations give the fixed ingestion-unavailable503 without a patient projection or any file bytes. Do not return a cached precommit observation instead. Discovery can instead suppress its ingestion entry/capabilities according to the final discovery contract, without leaking guard identities or infrastructure diagnostics.

## 3. Common transaction protocol and ordering

Keep the persistence order: User NO KEY UPDATE → existing IdentitySecurity → IngestionActor → singleton Control → organisation NO KEY UPDATE → existing content receipt → patient NO KEY UPDATE → intents in UUID order → contents in UUID order → reservation → work → append attempts/events. Skip untouched rows; never reverse. A Control-only maintenance transaction takes only Control and never later acquires earlier rows. Any subsequent broader transaction starts again in the common order. No transaction holds Control while waiting for an external observer/process/scanner or acknowledgement from an operating-system operation.

For an authority-bearing phase: validate the typed context and remaining budgets; take its fresh observation outside locks; acquire the applicable rows in order; resample active actor/session epoch/network/global and exact-branch grants/creator rules as applicable; require active observation matching locked Control; require the operation-specific API/intake/download gates and current UUID fences; select fixed bounded response/audit facts and recheck original cutoff immediately before COMMIT. Encode detached JSON before committing its disclosure audit. An observation never replaces current database permission checks. Ordinary worker authority uses committed receiver/epoch/origin provenance, not a browser session that must remain logged in.

The separately charged actor allowance intentionally precedes guard/target lookup: genuine authentication/action → original context capture → scalar validation → actor admission → guard/Control authority. Admission has no patient projection and no guard prerequisite. It may known-commit the allowance even when the following observation fails or Control is disabled, then return503. No patient lookup/body read or transfer slot acquisition is allowed merely because allowance committed. Unknown admission ACK is not permission to continue or charge again speculatively. Unsupported methods/global/scalar failures keep the transport draft's existing ordering and do not reach this admission.

All five operations require current API/identity gates. New first reservations additionally require intake_open, fresh readiness, queue/storage capacity and eligible current write key. Bound replay bypasses only these first-reservation gates; it still needs active guard, current API/authority and rate/transfer capacity. Download additionally requires download_open/current clearance and its transfer capacity. Ordinary scoped reads and logical withdrawal do not require intake readiness, queue space or storage headroom.

### Readiness publication and renewal

The publisher must carry a trusted immutable `OwnedSupervisorLaunch` proof bound to installation/epoch, exact supervisor generation **and supervisor process instance**, fixed owned service/cgroup/process-start identity and approved runtime manifest. It originates only from the reviewed root-controlled OS launch path, established before the supervisor can publish. Neither reading current UUIDs from Control nor accepting UUIDs from a caller/job/readiness payload can construct or refresh that proof. A paused former supervisor retains only its old proof; it cannot adopt a replacement generation/instance by rereading the database. Each renewal must prove equality with the currently authorised owned launch as well as fresh scanner policy/readiness evidence. Root may establish the expected launch identity through the reviewed fixed operational launch procedure; this supplies no public operator API, general broker or HMAC service. Exact unforgeable OS provenance transport, process identity checks and the durable expected-instance representation remain explicit acceptance/schema gates, not an assertion that UUID possession authenticates a process.

Collect bounded scanner/OS evidence outside locks, then take fresh G. In a short Control transaction require active matching installation/epoch, api_enabled=true and equality of the trusted launch proof with the current authorised supervisor generation/instance. Require the exact runtime manifest/policy/hash/time/readiness evidence. Publish or renew only readiness token/evidence and its <=60s validity; a renewal cannot replace the launch identity or extend evidence beyond its real observation policy. Never set api_enabled, intake_open or download_open, and never generate a new installation/epoch or forgive stale claims. Unknown commit does not authorise claims; resolve with a fresh G transaction and the same owned launch proof. After known commit perform a fresh outside-lock guard check before advertising ready or beginning another authorised phase. Failure keeps the publisher locally unready; it does not reopen any gate or presume a committed token vanished. Closing API denies publication/renewal even if an earlier G was active, because locked Control is rechecked after waits.

Avoid a readiness bootstrap cycle: after preservation/fresh-namespace checks, a separately reviewed root fresh-installation/unchanged-maintenance activation may set api_enabled=true with intake_open=false/download_open=false/readiness=false and a matching active guard **while ordinary ingress and all ordinary ingestion callers remain stopped**. These bits are not a read-only permission ceiling: bound replay and content withdrawal also use api_enabled without intake_open. Keep HTTP/UI/MCP, direct-service jobs and ordinary byte/worker callers stopped throughout bootstrap; only the exact trusted supervisor launch/readiness publisher may run. Establish its expected owned generation/instance, launch it and publish readiness while intake/download remain false. Only a later separately reviewed root step may open intake after current evidence/acceptance; download is independently approved and stays false until its prerequisites pass. Start the intended ordinary processes and remove ingress maintenance only after the intended gate state is reconciled and authorised. A post-activation API-enabled/intake-closed state may permit replay/withdrawal under their normal rules and must never be described as read-only. The publisher cannot open any gate. Restored namespaces still have no first-slice reopen path. Maintenance reopening in section6 follows this staged order, never intake-already-open startup.

### Optional CurrentUser discovery selection

First complete ordinary CurrentUser authentication and assembly under its unchanged existing contract and leave all existing transactions. Only then, without a patient lookup or transfer/rate admission, take fresh G and run a separate short selection transaction in common order: current User → IdentitySecurity → Control, then applicable organisation/grant rows without reversing that order. Revalidate the current request's live actor/session epoch/origin policy and exact named-branch read conjunction; use current branch grants and Control/readiness/capacity facts, never the already assembled global permission union. Require matching active guard and api_enabled. Materialise only the bounded closed optional `document_ingestion` map into detached immutable values before releasing locks; no model/lazy query escapes and no patient/content/intent row or new patient-disclosure event is involved.

After successful transaction completion, take a new outside-lock postselection guard observation matching the selected installation/epoch. Only then attach the optional map to the legacy result. Missing/corrupt/closed/mismatching guard, invalid/missing Control, disabled API, failed revalidation, selection uncertainty or failed postselection observation suppresses **only the optional ingestion property**. It does not convert the already valid legacy CurrentUser response into ingestion503, replace its fields or bypass its own denial behavior. Its existing authentication/middleware failures retain their established response semantics. No fresh ingestion-disclosure audit COMMIT is required for this control-only selection. The database selection is the capability linearisation point; the postselection observation suppresses a now-unavailable advertisement but creates no atomic DB/file view or enduring permission.

For each currently eligible branch, available/can_read describe deployed scoped read/status eligibility. Routine scanner outage, stale readiness, closed intake or queue/storage exhaustion changes can_receive to false, without making available/can_read false. can_receive additionally requires the exact current write conjunction and all first-reservation intake/readiness/capacity gates. Omit branches without the read conjunction. Never cache the optional map, guard inode/observation or a previous successful map across CurrentUser requests; no startup/default/last-good fallback. Every later ingestion call performs its own current authority checks.

## 5. Failure, cleanup and limits of disclosure evidence

If Greply fails after a known receive/withdraw/audit commit, return fixed503 with no projection and retain the committed effect/receipt/audit. The audit is a disclosure attempt, including one suppressed before delivery; it does not assert bytes or JSON reached the browser. Do not roll back committed work, refund actor allowance, mint a new command key or retry encryption to produce a nicer response. If an audit COMMIT outcome is unknown, do not send a response containing patient data or any plaintext. Later independently authorised status/replay can reconcile known receipts when current gates permit.

For work without an HTTP response, a postcommit observation failure prevents starting the next external phase; it does not rewrite an immutable result already committed. Fencing/stopping, conservative terminal/unavailable evidence and conditional transfer-slot cleanup may still run while the guard/API is closed: they only reduce authority or account for proven cessation, never bind/promote/disclose/start work. Keep this cleanup vocabulary narrow in the final service contract. Stop confirmation occurs outside locks; matching token/instance release markers and counter decrement commit once under the common order. Unknown termination/release ACK retains the slot until resolved. No storage charge refund, byte deletion or key retirement follows from closure.

A failed guard read must not start an unbounded repair loop or attempt to create/overwrite the file. Fixed503 and an internal bounded control failure record are sufficient; staff receive no installation/epoch/path detail. Runtime guard/readiness retries cannot stretch first binding or scan deadlines. Time rollback/invalid clocks fail the existing budget rules, not a reinterpreted guard timestamp.

## 6. Root maintenance and stop-before-replacement protocol

This is a required future **operational contract**, not a new application operator endpoint or a delivered script. Root alone changes the guard; no broad broker, HMAC service, hold/purge service or recovery re-enable path is added.

1. Put the relevant ingress in maintenance so no new ingestion request can enter. In a short Control-only transaction, durably close api_enabled/intake_open/download_open and readiness, fence the current readiness/supervisor identity and prevent new claims. Resolve the COMMIT outcome; uncertain closure does not permit physical replacement. This is the database closure linearisation boundary. In-flight operations that selected authority earlier may have committed; preserve them rather than promising rollback.
2. Publish a closed maintenance guard at the same installation/epoch using exclusive private temp, file fsync, atomic replacement and directory fsync. Unknown guard persistence keeps maintenance closed. An emergency closed guard may be written earlier to reduce activity, but does not substitute for known database closure or cessation. Do not reopen when database/guard observations disagree.
3. Fence/stop and confirm cessation of every owned application discovery/admission, byte writer/server, worker and supervisor process that can hold an observation/selection, including descendants and active response streams. Keep fixed service restart paths disabled during maintenance. Stop scanner/decoder activity through the owned runtime protocol. A closed listener, expired lease, empty queue, DB fence or one dead PID is not cessation. If any process/COMMIT/stream outcome remains unresolved, retain all state and **do not replace** DB, objects or keys. All process/OS I/O is outside business locks.
4. For restore, once processes are confirmed stopped and before replacing any authoritative DB/object state, durably publish a **new** target epoch, closed/reason restore, same installation identity and selected manifest hash outside the restored namespace. Privately retain the root receipt independently of DB/object backups. Unknown file/directory durability is a stop condition. Only then may the separately authorised offline restoration rehearsal replace state; it starts no ingestion/byte/worker process.
5. First-slice restore stays closed with no re-enable path. Copied enabled Control, clearance, ready flags or old guard backup never authorise startup. A future separate recovery design must install/reconcile target identity and all false gates; this draft supplies neither that workflow nor a current recovery principal. Unchanged-namespace maintenance reopening requires preservation checks and confirmed old-process cessation: keep ordinary ingress/callers stopped; durably activate the same-epoch guard; reconcile Control with all gates/readiness false; known-commit api_enabled=true alone, which is not a read-only ceiling; establish and launch only the trusted current supervisor/readiness publisher; obtain current readiness evidence; separately review/known-commit intended intake and download gates; then start the intended ordinary processes and remove maintenance. No generic gate opening before readiness, no ordinary replay/withdrawal caller during bootstrap, no automatic restart-generated epoch/counter reset. Any uncertainty leaves maintenance closed.

The protocol assumes an administrator obeys maintenance, stop, file durability and namespace separation. A local file has no independent hardware monotonicity: arbitrary root database replacement, editing both controls, whole-VM/disk snapshots that roll back the external file too, or restored historical operational receipts can bypass it. The application cannot claim to detect these cases automatically. Parent close/release evidence must state this threat boundary; independent guard storage/receipts within a correctly followed restoration procedure are not standalone anti-rollback protection.

## S1 record grammar alignment —13 November2026; parent remains DRAFT

The version1 recorded_at spelling is exact ASCII YYYY-MM-DDTHH:mm:ss.ffffffZ, valid Gregorian year0001..9999/seconds00..59, UTC with exactly six fractional digits. It is provenance only, not a clock/lease/TTL. All seven existing fields remain required. Every trusted observation/authority boundary, including discovery, publication, claim, binding, promotion, disclosure and postcommit selection, must independently reject reason=restore in this first slice even if mode is active, as well as require active mode, trusted fresh OS provenance, matching locked Control and current scoped authority. Only the separately reviewed S1 facts-decoder leaf may be frozen; OS reading/provenance, launch-instance schema, full parent services/runtime/API and restore re-enable remain unfrozen/unimplemented. No guard file, group, schema, endpoint or setting is created by this alignment.
