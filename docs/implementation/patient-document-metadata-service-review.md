## Assessment

The proposed two-phase design is coherent and implementable after the narrow amendments below. It correctly separates retained actor admission from patient-bound disclosure audit, keeps a stable actor lock without creating identity profiles, and avoids privileged platform/network authority. There is no reason to block B2 on file ingestion, staff UI, production activation, network blackhole response deadlines or a new global authentication architecture. PostgreSQL service races, constraints and failure tests remain B2 acceptance gates; source inspection and coordinator feasibility spikes cannot substitute for those tests.

## Amendments required before freezing service code

### 1. Make read-only session mint and revalidation executable

`django.contrib.auth.get_user(request)` is not a read-only validation primitive: installed source calls `session.cycle_key()` when a fallback hash matches and `session.flush()` for an invalid hash. `identity_security.session_hash()` also creates a missing session. Cached `request.user`, cached session values and `isinstance(HttpRequest)` alone do not establish durable session authentication. The draft's promise to use the installed authentication/session backend without session writes needs a concrete algorithm.

Recommended narrow ruling for this app's currently configured database sessions: require a genuine raw HttpRequest, configured DB SessionStore and an already present session key; freshly read the existing unexpired signed session record without row locks; decode through the installed store; validate auth user ID, allowed installed backend path, and session auth hash against the fresh active backend user. Use Django's constant-time hash comparison and preserve its configured fallback-hash acceptance, but do not rotate, save, flush or create sessions in this service. Missing/invalid backend/user/hash, partial MFA challenge-only sessions or mismatching request actor deny authentication. An unsupported session engine fails closed rather than accepting a supplied session dict. The configured DB engine can be frozen explicitly without adding a provider framework.

Mint immutable scalar authority only after this validation. Bind actor, session-key digest, originally captured epoch, operation and network descriptor; compare the live request's key/actor/epoch to these captured values whenever authority is checked. Revalidate persisted session binding at phase-A and phase-B authority checks and in the final materialisation pass, not only cached request state. Carry the persisted expiry timestamp into the pure final check and reject expiry at equality with selected_at. Do not return/store raw key or auth hash in context repr, errors, events or logs. Fresh User NO KEY UPDATE remains before existing IdentitySecurity; never overwrite the captured epoch from the locked row. Reject bool/negative/noninteger epoch, with missing legacy epoch accepted only at authoritative epoch zero.

This does not attempt to sandbox trusted Python capable of constructing requests or reading session secrets. The supported service boundary rejects a plain dataclass constructor, arbitrary actor IDs, trusted booleans and unverified dict sessions; independently reviewed future adapters require their own scoped authenticator.

### 2. State concurrent logout semantics precisely

Current `api.Logout` calls Django logout without the actor User lock. It deletes/flushed session state; an already loaded request retains cached data. The proposed actor lock therefore serialises epoch revocation and existing identity mutations, but cannot serialise a different request's ordinary logout. A private request reference catches same-request logout/binding changes, not another request's deletion by itself.

Recommended ruling: a persisted deletion committed before the final fresh session sample denies the operation; logout racing after that sample may coexist with the already selected audited result. Keep this sampled-session guarantee explicit, including the small interval between final DB sampling and selected_at. Do not claim immediate cross-request logout cancellation or guarantee no result after logout acknowledgement. No new session row lock or change to global logout is necessary for B2. Test deletion before the final sample, deletion after it, same-request flush, epoch revocation in both lock orders, and first-profile creation. If the owner instead requires stronger logout serialisation, that is a separate identity/logout contract amendment, not something an in-memory mint token solves.

### 3. Resolve disabled admission and flag parser once

Accept reception-only document read/write grants in B2: real service authority and CurrentUser can then be tested together. CurrentUser's permission arrays are authority ceilings, not readiness; feature flag false must not remove the grants or create R04 navigation/HTTP routes. Test exact branch_permissions and mixed reception-B/doctor-A, plus other roles unchanged. B2 still leaves four catalogue operations planned and 46 HTTP operations implemented.

Use existing `env_boolean('HMS_DOCUMENT_METADATA_ENABLED')` for consistency: default false, accepted existing literals 0/1/true/false after its current normalisation, malformed environment fails startup. Service checks require `type(setting) is bool`, so malformed runtime/test overrides fail503. Restricting only this flag to literal true/false adds no safety benefit and would differ from existing configuration conventions.

Freeze the proposed retained-admission policy: after valid action authority, pure input validation and pre-admission network acceptance, a valid disabled attempt commits its phase-A increment, then returns503 outside that transaction, before phase B or any patient/document query. **Raising the disabled error inside the phase-A atomic block would roll back the required increment.** Once admitted, later flag disable/dependency/network/business failures retain admission. Check enabled again before patient lookup in phase B; a false flag returns503. Invalid/no-action/unauthenticated calls do not consume; saturated limiter returns429. Configuration invalidity may fail503 before admission because the dependency is unusable; do not claim a guaranteed committed allowance in that case. Pin this precedence in the matrix.

### 4. Correct the scope/error contradiction

The phase-B prose says “no global grant403 before patient lookup” while interfaces/phase A require global-action rejection first. Freeze: no authenticated global same-branch conjunction anywhere =>403 before patient lookup; once global action exists, missing/foreign/inaccessible patient or mismatched document =>the same404. An exact patient's inaccessible branch must not become a scope-revealing403. Creator-only withdrawal403 applies only after current visible patient/document scope is established and before replay/state. Fix the retained-admission matrix's generic “branch403” wording accordingly. Malformed B1 input errors are evaluated only after global action authority and before admission as already proposed.

### 5. Freeze final policy snapshot semantics and pure reselection

The proposed pure deadline reselection is appropriate. `NetworkSnapshot` exposes confirmed_policy, candidate_policy, pending_change_id, activated_at and rollback_at, and `_snapshot` already validates reciprocal graph, fallback==confirmed, bindings and fixed deadline. For no pending change use confirmed; for a validated pending graph use candidate iff activated_at<=selected_at<rollback_at, otherwise confirmed at/after rollback. Do not trust the earlier effective_policy or pending_status to choose at final time; expired_unreconciled still has the graph fields. selected_at before activation or backward from operation start fails503. Do not mutate snapshot dictionaries or reconcile state on read.

Compare freshly computed environment digest and normalised captured socket/header IP with the mint. Drift/unavailable state =>503; valid policy/environment denial =>generic403. Evaluate both environment ceiling AND selected overlay. Never use network management's configured-owner/OS-operator/MFA chain or add a second org lock.

One coherent network SELECT is a statement snapshot, not a lock against subsequent policy writes. Freeze the guarantee as **latest materialised final snapshot**, with pure deadline projection at selected_at. An allow->deny commit visible before that SELECT must deny/rollback; a commit after that statement snapshot may still permit its already sampled audited result, even if it precedes selected_at by a small interval. Otherwise “any policy change before selected_at is seen” would be an impossible guarantee without additional synchronisation. Existing contract already allows policy change after selection; clarify this sampling interval rather than adding owner/network locks or an unbounded reread loop. Test both serial observation orders and a blocking SELECT crossing exact rollback; a newly activated graph newer than the pre-read clock may conservatively fail503 through current loader validation.

### 6. Freeze a measured exact-minute database constraint

The proposed UTC TruncMinute CHECK is plausible but source reading alone does not prove backend/type/timezone behavior. Installed PostgreSQL operations generate `DATE_TRUNC('minute', field AT TIME ZONE 'UTC')`, a timestamp without timezone compared with the original timestamptz. Implicit timezone casts must be understood. Installed Django `ExtractSecond` explicitly truncates fractional seconds first, so it must not replace the CHECK as a fractional-second guard.

Coordinator's isolated feasibility probe should record generated SQL and actual acceptance of aligned values and rejection of nonzero seconds and microseconds, on PG17 and SQLite where portable-model support is promised. Test timezone behavior or explicitly freeze UTC connection requirements; prefer an independently verified expression over relying on an unspecified cast. No need for a new provider or changed timestamp type. Empty reverse/forward and nonempty reverse-before-DDL guard remain mandatory. This is a schema freeze gate, not a claim that a probe has already passed or that B2 migration tests exist.

## Lock/security rulings that can be adopted without redesign

- Keep actor User NO KEY UPDATE -> existing IdentitySecurity -> single patient Organisation NO KEY UPDATE -> current exact-branch membership read -> existing receipt -> Patient NO KEY UPDATE -> selected intents NO KEY UPDATE in UUID order. Org gate is sufficient for supported staff writers; omit Membership and StaffAccessRevision locks. Explicit `of=('self',)` prevents joined FK lock expansion.
- Existing staff replacement locks its own actor, then org, then target memberships/revision, and can insert a target-user FK. Actor NO KEY UPDATE permits FK KEY SHARE, avoiding the concrete document-actor/org/staff-FK cycle. Do not “strengthen” it to full FOR UPDATE. Actual two-order PG races must still demonstrate it.
- Current patient PATCH cannot transfer branch and Branch API cannot transfer org. Keep derived scope, refresh after waits and fail mismatch without following into another org. Direct DBA edits or future transfer services do not become supported through this ruling.
- Phase A owns its successful outermost commit; phase B reacquires identity and scope, retains successful disclosure audit and produces detached bytes only after business commit. SET CONSTRAINTS ALL IMMEDIATE before final reads/selected_at and no later writes is appropriate. No on_commit audit or lazy response query.
- Cooperative five-second budget and PG17 local lock/statement/transaction controls are useful; do not advertise COMMIT acknowledgement or HTTP delivery bounds. An uncertain commit means503/no projection when the call returns, discard suspect connection, explicitly retry identical key later. Do not refund admission or delete ambiguous history.
