# Patient document metadata: proposed lock and disclosure contract

24 October 2026. **DESIGN ONLY / UNFROZEN.** Applies after the [schema-only foundation contract](patient-document-foundation-contract.md) and [foundation plan](patient-document-foundation-plan.md), frozen at coordinator checkpoint `d8feaad`. It does not amend that schema freeze or introduce services, permissions, HTTP routes, OpenAPI operations, bytes, workers or storage. The foundation was still being implemented during this read-only review; no runtime or race test was run here.

## Source evidence and the compatibility constraint

- `identity_security.lock_identity()` locks actor User with PostgreSQL `FOR NO KEY UPDATE`, creates a missing IdentitySecurity row, then locks that row. Identity mutations use this stable actor lock before factor/session changes. `require_session(user, state)` evaluates the captured `_hms_auth_epoch`; it does not magically refresh a stale `user.is_active`. `lock_platform()` separately checks the freshly locked User and privileged MFA. Do not call `lock_platform()` for ordinary document access: it is a platform authority helper.
- `staff_access.locked_organisation()` takes the **staff actor's** identity locks, then Organisation `FOR UPDATE`, then reauthorises the staff actor. `change_staff()` subsequently locks the **target's Membership rows** ordered by branch/role, then target StaffAccessRevision. Its target User lookup is ordinary SELECT, not a target identity lock. Membership replacement may INSERT new target-user FKs. A document actor B may simultaneously be this staff actor A's target.
- Resource administration takes actor identity, Organisation `NO KEY UPDATE`, Branch `NO KEY UPDATE`, then Bed. Reception allocation locks Bed then Patient; it never waits for Organisation/actor after taking those rows. Existing reception retry ledger is claimed before its domain locks; it is a distinct table from the new document receipt and must remain unchanged.
- Network management takes actor User `NO KEY UPDATE`, IdentitySecurity, configured owner Organisation `NO KEY UPDATE`, NetworkOperator, singleton NetworkPolicyState, then preview/change rows. HTTP network enforcement uses `network_environment.network_decision()` as a read, not that privileged operator lock chain. Do not call operator authorisation for document access or append a second organisation lock after document locks.
- Patient registration branch cannot change through existing Patient PATCH; Branch.organisation is not an editable API field. The foundation deliberately derives scope through these FKs. Any future merge/transfer must review this lock invariant first.

**Critical rule:** keep document actor User, Patient and intent locks `NO KEY UPDATE` where their identifying keys are immutable. A stronger actor User `FOR UPDATE` can form a cycle: document B holds User B and waits for org; staff A holds org and inserts a replacement Membership referencing B, whose FK `KEY SHARE` waits for User B. `NO KEY UPDATE` permits the FK check while still serialising other actor identity operations. Similar full Patient/intent locks can unnecessarily block existing or future referencing inserts. This is a proposed deadlock prevention argument requiring the actual PostgreSQL race below, not an observed exploit/test result.

## Proposed single-operation lock order

All supported document metadata mutations and audited disclosures use the same order in one outermost transaction. Inputs are scalar/shape validated before beginning it; preliminary capability/scope reads may reject a caller but never authorise a later write/result.

1. Lock **only the current actor User** `NO KEY UPDATE`, using captured actor ID. Check the fresh row is active; preserve the original server-captured epoch/session/proof fields rather than copying fresh epoch into the request.
2. Lock that actor's existing IdentitySecurity row. If absent, treat authoritative epoch as0 under the explicitly retained existing epoch0 compatibility rule; do not create a profile as an unrelated read side effect. The stable User lock serialises concurrent first-profile creation by existing identity services. The next frozen service contract must state whether compatibility is retained or narrowed, with tests; no implicit new service-call bypass is authorised.
3. Resolve a tentative patient→branch→organisation descriptor under preliminary visibility, then lock that **single patient organisation** `NO KEY UPDATE`. Refresh/recheck the chain after waiting; do not acquire a second organisation to follow changed data. Mismatch fails closed. Do not lock Branch through a joined FOR UPDATE query accidentally; use `of=('self',)` where appropriate.
4. Re-read current actor membership for the exact patient branch and required conjunctive action/category. If explicit Membership row locks are used, acquire only actor rows for this branch in `(branch_id, role, id)` order **after org**, `NO KEY UPDATE`, and validate current rows after the wait. Do not lock creator/other staff User, their identity rows or a later actor StaffAccessRevision. Organisation serialises supported membership insert/delete/suspension, including the absent-membership case; a row lock alone cannot protect absence.
5. For create/withdraw only, lock an existing actor+operation+key **DocumentIntentReceipt** `NO KEY UPDATE`, never the reception IdempotencyRecord. No row exists to lock on first execution; the actor User lock serialises same-actor document commands even across organisations. Retain the DB unique constraint as backstop; do not introduce advisory/global retry locks. A unique-collision savepoint may reread only after rollback to a usable transaction, and must never invert this order. Unexpected collision failure is unavailable, not successful replay.
6. Lock exact Patient `NO KEY UPDATE`, then recheck its branch/org matches the descriptor. Do not hold Bed/Appointment/Encounter locks, and do not call reception allocation while holding document locks.
7. Lock exact addressed PatientDocumentIntent `NO KEY UPDATE`; for a list, lock **only the selected ≤100 intents**, deterministically by UUID, after collecting bounded IDs in display order under the org/patient gate. Materialise every selected scalar field and build output in display order. No receipt lock is needed for list/detail. For create there is no pre-existing intent to lock; create it after Patient. All future metadata writers must use the same org/patient gate so supported creates cannot introduce page phantoms while a list is selected.
8. Perform the state transition (if any), bind the required complete receipt, insert DocumentAccessEvent, then run final authority/time/network checks after all potentially blocking inserts/FK/unique checks. Commit successfully before returning detached primitives. Do not return a model, lazy queryset, callback, generator or lazy serializer that can disclose fields or re-query outside the transaction.

Do not lock all memberships of a large organisation, all patient intents, all staff users, or the entire network-policy owner graph. Sorted row ordering complements, rather than replaces, the higher organisation gate. Existing operational writers that do not use that gate cannot mutate document rows. Direct SQL/DBA mutation, unscheduled patient reparenting and unsupported services are outside the claimed serialisation boundary.

## Authority, time and transaction bounds

At entry capture a server-derived context: actor/session identity and epoch, optional existing proof binding, verified socket/proxy network descriptor and exact requested action. Recheck fresh actor active state, **captured** epoch against locked security state, current branch/category grants and patient association after lock acquisition and again after the access-event/receipt insert. Do not turn “user is known” or master role into a document grant. Exact role grants and a minted direct-service context remain future decisions, not capabilities delivered by this design.

Run the ordinary effective network decision again at the final selection instant, retaining environment AND overlay and trusted-proxy parsing. Do not acquire `lock_network_operator()` or require a master role. Document and configured network-owner organisations can differ; adding owner locks after target-org lock would create cross-org ordering risk. A pure coherent policy snapshot does not promise it remains unchanged after its selection instant. Network denial/unavailability rolls back new metadata/audit/receipt writes and returns a generic failure without PHI.

Proposed budgets to freeze after measurement: lock_timeout2seconds, per-statement timeout3seconds, total service deadline5seconds with checks after blocking steps and immediately before return from atomic work; no automatic in-request retry loop. Use transaction-local settings, never connection-global mutation. Bound each page default25/max100 and membership lock set to exact actor+branch roles. Prefer bounded keyset page selection with `has_more` based on ≤101 IDs; freeze exact cursor/query grammar later. Do not promise an exact unbounded total COUNT or allow unbounded offset merely because the event stores returned count. Any optional total count needs separate query budget/evidence. Audit records result_count0..100 even when a private sentinel determines has_more.

Select one `selected_at` after all domain locks and potentially blocking audit/receipt inserts; backward clock relative to operation start fails503. Use it consistently for all projected pending/expired states. At equality `selected_at >= expires_at`, pending projects expired; no DB update/version bump. Withdrawal requires final `selected_at < expires_at`, creator==actor, current write+visibility and expected_version. Recheck after any later forced constraint wait; if the boundary passed, roll back the transition, receipt and event. Create's stored created_at/expiry stay fixed even if a slow response already projects expired. No retry extends expiry.

PostgreSQL deferred FK validation may occur at commit. Before final authority/time selection, force the new operation's deferred FK checks to run while still inside the transaction, using an explicitly frozen approach and tests; do not assume a successful INSERT cannot later wait/fail. A bounded whole-transaction timeout must include the final COMMIT round trip through the connection/driver policy. A clock check alone cannot interrupt a hung commit. Unknown commit outcome never returns a success projection; later keyed retry verifies committed state and reauthorises. Deadlock/lock/statement/connection/audit failures produce a generic503 after the transaction exits/rolls back. Do not catch database errors inside a broken atomic block and continue.

Distinguish the final authorisation/selection instant from later successful commit and delivery. Identity/membership locks remain held through commit; the pure network snapshot can change after its selection. Only release the detached projection after commit of its access event. A later revocation/network change or clock crossing cannot retract an already selected result. This design offers ordered authorisation at selection, **not revocation after disclosure or instantaneous browser erasure**. Frozen HTTP work must bound serialization/response size and retain no-store; no bytes/streaming contract exists here.

## Audit-before-disclosure by operation

Existing AuditEvent/admin history is untouched. Dedicated DocumentAccessEvent binds a canonical sorted list of **returned UUIDs** via projection_sha256, as required by foundation; it is not a hash of all returned field values and is not tamper-proof logging. Use server-generated correlation UUID. No filename/patient name/reason/body/proof enters event details or errors. Audit schema currently requires patient; it is not a general denial log, so unauthorised requests need no fabricated cross-scope access row.

| Proposed internal operation | Selection/receipt rule | Event and atomic result |
|---|---|---|
| List intents | Authorise exact patient/category; select/materialise bounded page while org/patient gate held. Empty permitted page is still a disclosure. | One `intent.list`, document=null, count0..100, digest of returned UUIDs. Commit before returning the page. No hidden query/count disclosure outside the event boundary. |
| Detail intent | Lock scoped intent and verify intent.patient==locked Patient; include projected expiry at selected_at. | One `intent.detail`, exact document, count1. Denied/not-found returns generic failure without event/projection. |
| Create result, first execution | Validate stable key/fingerprint; authorise first; create immutable declaration pending, exact30minute expiry, then complete receipt. | One `intent.create_result`, count1; intent+receipt+event either all commit or none. No upload/content acceptance implied. |
| Create result, replay | Current category and exact result-patient scope reauthorised; matching fingerprint returns **current** pending/expired/withdrawn projection. Changed fingerprint409, no original metadata echo. | A new `intent.create_result` event for **each successful disclosure**, no duplicate intent/receipt and no expiry change. Audit failure prevents replay disclosure too. |
| Withdraw result, first execution | Creator-only, current conjunctive grants, pending and strictly unexpired at final selection, expected_version exact, increment once; record reason under existing10..500 rule. | One `intent.withdraw_result`, count1; transition+complete receipt+event atomic. Event contains no free-form reason. |
| Withdraw result, replay | Matching immutable command fingerprint, reauthorised result scope; return current terminal projection. A later request under a new key cannot withdraw again; freeze its exact409 behavior separately. | New `intent.withdraw_result` event on successful replay, no extra version increment/mutation. |

Services must own the **outermost** commit boundary for disclosure; returning from nested `atomic()` is insufficient if a caller later rolls back the outer transaction. Propose reject invocation inside an ambient transaction for these public service entry points, or use durable atomic semantics with an explicitly tested policy; internal helper composition must not expose results before the real commit. No `on_commit` audit insert: it can fail after data/result commitment. No audit “best effort,” sampling, background queue or success on event failure. Do not claim receipt replay reproduces the original response body; it returns the currently authorised result and logs that new disclosure.

## Required real PostgreSQL race matrix

All are future RED-first tests. Use separate connections/threads and barriers; inspect `pg_blocking_pids()`/lock state to prove the named loser actually waited, not merely started later. Run both serial orders for each pair, assert bounded completion/no40P01 and clean transaction state. SQLite cannot prove any lock claim.

| Pair / both serial winners | Required outcome |
|---|---|
| Staff A replaces/suspends document actor B's memberships vs B list/detail/create/replay/withdraw | Staff-first: B waits org, then denied with no new document receipt/event/projection. Document-first: staff waits org until audited result commits; subsequent B operation denied. Include an inserted replacement Membership to exercise FK KEY SHARE against B's actor User no-key lock; prove no user↔org deadlock. |
| B identity revoke/disable/password epoch bump vs B disclosure/write | Revoker-first: document waits actor User then rejects original captured epoch. Document-first: revoke waits User until commit; only already-selected result may return. Include originally absent IdentitySecurity and concurrent first-profile creation, with no profile creation by list/detail. |
| Network policy allow→deny vs document final selection | Change-first: document final policy read denies/rolls back. Document-selected-first: original audited selection may return, next access denied. Force both orderings at final policy read; no claim a pure policy read blocks policy writers. Do not fake a blocking claim for this pair. |
| Same actor/same key create vs create | Second waits actor User; identical command yields one intent/receipt and two disclosure events; changed fingerprint409 with no second event/projection. Test same key in different authorised patients/orgs and loss of access before replay. |
| Same intent withdraw vs detail/list | Withdraw-first: subsequent projection withdrawn; read-first: read event commits before withdrawal, selected immutable projection remains consistent. List locks at most100 intents; page after concurrent insert has no duplicate/omitted in-page state from mixed snapshots under the chosen cursor contract. |
| Same key withdraw vs withdraw; different-key withdraw vs withdraw | Matching replay increments once, logs each authorised result; changed-key stale version conflicts. Both actual serial winners exercised; no expiry extension. |
| Deadline and event/FK wait | Block insertion/constraint validation, advance controlled time to exactly expiry and beyond, release blocker: withdrawal fully rolls back; detail/list project expired at identical selected_at. Test backward time503 and version maximum without overflow. |
| Reception bed allocation / patient demographic PATCH vs document page/create | Observe actual Patient lock wait in both orders; no bed/org cycle or patient-scope drift. A mutable demographic may change after selection; returned scalar snapshot must not lazy-read a newer patient/name. |
| Actor A/B document operations in same org; A staff actor also edits B | Org serialises document operations; no later target User/security lock acquisition from document service. FK event/receipt checks remain compatible; no deadlock and no unbounded lock set. |
| Access event failure/commit failure/outer transaction misuse | Inject INSERT and deferred-check/COMMIT failures: no PHI result escapes, no partial transition/receipt persists on rollback. Unknown commit outcome requires retry, not false success. Attempted outer-transaction use is rejected before document disclosure. |

Independent review must confirm actual query/lock footprint (`of=self`, join behavior, FK checks), receipt replay ordering, list snapshot/materialization and timeout/commit semantics before a metadata service freeze. Future HTTP routes/OpenAPI/page actions/UI and document role grants remain unfrozen. This proposal does not warrant starting those capabilities or claiming full Task04/read-audit release delivery.

Primary references checked for the lock argument: [PostgreSQL17 explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) documents row-lock compatibility/deadlock ordering; [Django5.2 select_for_update](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update) documents no_key/of and evaluated-query behavior. These support the proposal; actual HMS races/latency are still unexecuted.
